## ADR-001：MVP 采用模块化单体，而非微服务

### 状态

Accepted

### 日期

2026-03-23

### 背景

产品当前处于 MVP 阶段，团队首要目标是尽快验证“AI 陪练式学习执行层”是否成立。核心业务模块包括认证、工具选择、学习编排、任务状态、学分段位、历史学习计划、会话恢复和埋点分析，这些模块当前业务耦合紧密、边界仍在快速演化。

### 备选方案

1. 模块化单体
2. 微服务

### 决策

采用模块化单体架构。

### 理由

- 交付速度更快
- 本地开发和联调复杂度更低
- 便于快速迭代数据结构和业务规则
- 当前业务量和团队规模不足以支撑微服务收益

### 代价与权衡

- 后期模块边界若不自律，可能形成单体膨胀
- 需要在代码层面主动保持领域隔离

### 后续动作

- 服务端代码按 `auth / onboarding / progress / learning / task / gamification / history / analytics` 分域组织
- 为后续拆分保留清晰接口边界

## ADR-002：采用 Next.js 16 全栈一体作为 Web 应用基础

### 状态

Accepted

### 日期

2026-03-23

### 背景

MVP 同时需要营销页、登录流程、学习主界面、路径地图、成就页和历史学习页，也需要服务端 API、鉴权和页面数据聚合。项目优先考虑研发效率和同仓协作。

### 备选方案

1. Next.js 16 全栈一体
2. React SPA + 独立 Node API 服务
3. 前后端完全分仓

### 决策

采用 Next.js 16 全栈一体方案，并配套 React 19.2.4、TypeScript 5.7.3、Tailwind CSS 4.2。

### 理由

- 前后端同仓协作效率高
- 营销页和应用页都可统一承载
- App Router Route Handlers 可直接作为 BFF
- 适合 Vercel 托管部署
- 与当前代码依赖中的 React 19.2.4、TypeScript 5.7.3、Tailwind CSS 4.2 对齐

### 代价与权衡

- 前后端职责若不控制，容易在同仓中混杂
- 需要在代码结构上明确页面层、BFF 层和服务层

### 后续动作

- 建立统一目录规范
- API 层只做聚合和编排，不直接堆业务细节

## ADR-003：主数据库选择阿里云 AnalyticDB PostgreSQL 版 Supabase

### 状态

Accepted

### 日期

2026-03-23

### 背景

系统需要存储用户档案、路径模板、任务状态、会话消息、积分流水和成就记录，业务对象之间关系清晰，对一致性要求较高。

### 备选方案

1. 阿里云 AnalyticDB PostgreSQL 版 Supabase
2. MongoDB
3. 自建 PostgreSQL

### 决策

采用阿里云 AnalyticDB PostgreSQL 版 Supabase。

### 理由

- 数据天然适合关系型建模
- 支持事务和约束，适合积分、任务等一致性场景
- 保留 Supabase 范式，同时更适合国内账号与微信生态接入诉求
- 降低自建数据库运维成本

### 代价与权衡

- 受托管平台能力边界影响
- 大规模分析能力未来可能需要外置

### 后续动作

- 积分、任务、打卡采用事务性更新
- 分析事件先存事务库，后续再视情况分流

## ADR-004：认证体系采用阿里云 Supabase Auth

### 状态

Accepted with Risk

### 日期

2026-03-23

### 背景

产品面向中文市场，微信登录是重要需求，但 MVP 同时需要尽快上线，不适合先自建完整认证系统。

### 备选方案

1. 阿里云 Supabase Auth
2. 自建认证中心
3. 首版仅手机号登录

### 决策

主方案采用阿里云 Supabase Auth；若微信 OAuth 在首周配置验证受阻，MVP 临时降级为手机号主登录。

补充说明：

- 该 ADR 仍然有效，且当前仓库已经接入真实认证链路：手机号验证码登录、微信 OAuth 跳转、OAuth callback、登录后路由分流均已落地。
- 同时，首页已新增基于 `GET /api/auth/session` 的只读会话恢复能力，用于免登录续接“继续学习”入口。
- 因此这里记录的主要是“认证架构决策”，当前实现状态则应以 PRD、API 规范与前端工程说明为准。

### 理由

- 避免首版自建认证成本
- 在保留 Supabase Auth 范式的前提下，更贴近国内微信登录场景
- 保留 MVP 按时交付的兜底方案

### 代价与权衡

- 仍需尽早验证真实控制台能力与回调配置限制
- 需要确认环境隔离与 OAuth 配置流程

### 后续动作

- Sprint 1 优先验证阿里云 Supabase 的微信 OAuth 技术链路
- 同步准备手机号登录作为 fallback

## ADR-005：AI 服务采用外部 provider 抽象层，首版接入 SiliconFlow，并采用教学型结构化输出

### 状态

Accepted

### 日期

2026-03-23

### 背景

AI 导师是产品核心。系统需要稳定输出“当前目标、当前一步、为什么先做这一步、卡住时提示、下一步预告”等结构，而不是自由聊天。

### 备选方案

1. SiliconFlow + 结构化输出
2. 直接耦合单一模型 SDK，不做 provider 抽象
3. 自建多模型路由

### 决策

采用外部 AI provider 抽象层，当前首版接入 SiliconFlow，并要求模型输出结构化 JSON，由服务端做 schema 校验。

### 理由

- 教学型对话更依赖稳定结构
- 服务端 schema 校验可降低回复失控风险
- 当前阶段先落一个稳定 provider，并保留后续多 provider / 多模型扩展边界

### 代价与权衡

- 单模型供应商存在外部依赖风险
- 需要持续迭代 prompt 与 fallback 逻辑

### 后续动作

- 统一 Prompt 模版
- 对异常输出做兜底
- 记录失败样本做优化

## ADR-006：任务状态与积分计算统一在服务端完成

### 状态

Accepted

### 日期

2026-03-23

### 背景

学习主界面存在大量交互，若前端自行控制任务状态和积分变化，极易造成多端状态漂移、重复计分和历史不可追溯。

### 备选方案

1. 服务端统一计算
2. 前端先计算，服务端异步校正

### 决策

任务状态机、积分发放、段位变化全部由服务端权威计算。

### 理由

- 避免重复记分
- 确保历史可追溯
- 保证地图、成就、主界面显示一致

### 代价与权衡

- 前端需要更多依赖服务端接口
- 对接口延迟与幂等要求更高

### 后续动作

- `task/complete`、`checkin/daily` 接口必须支持幂等
- 积分流水保存在独立表中

## ADR-007：用户当前学习状态采用“模板 + 实例”双层模型

### 状态

Accepted

### 日期

2026-03-23

### 背景

系统既需要预置路径模板，也需要记录每个用户的实际推进状态。如果直接在模板表上写用户状态，会造成扩展困难和数据污染。

### 备选方案

1. 路径模板与用户任务实例分离
2. 单表同时保存模板与用户状态

### 决策

采用 `learning_paths / path_steps` 与 `user_learning_paths / user_tasks` 分离的设计。

### 理由

- 模板可复用
- 用户路径实例与任务实例可独立演化
- 后续支持路径版本和重学更容易
- `/learn`、`/map`、`/history` 可以围绕同一条路径实例统一聚合

### 代价与权衡

- 查询复杂度略高
- 需要服务端做模板到实例的映射编排

### 后续动作

- 工具选择后即时生成 `user_learning_path` 与对应 `user_tasks`
- 路径版本变更不直接影响既有用户实例

## ADR-008：事件埋点进入 MVP 核心范围，而非上线后补充

### 状态

Accepted

### 日期

2026-03-23

### 背景

产品当前处于验证阶段，最核心的问题不是功能是否存在，而是用户是否真的完成了第一步、是否持续回来、AI 是否真正推动了行为。

### 备选方案

1. MVP 即接入核心埋点
2. 先做功能，上线后再补埋点

### 决策

核心埋点必须进入 MVP。

### 理由

- 没有埋点就无法验证产品假设
- AI 对话有效率、首日任务完成率、7 日留存等都依赖事件数据

### 代价与权衡

- 首版研发工作量增加
- 需要前后端、数据侧先统一事件字典

### 后续动作

- 在开发前输出埋点字典
- 对关键链路建立看板

## ADR-009：部署优先采用 Vercel + 托管服务，而非自建基础设施

### 状态

Accepted

### 日期

2026-03-23

### 背景

MVP 阶段最重要的是上线和迭代速度，不是基础设施掌控力最大化。

### 备选方案

1. Vercel + 阿里云 Supabase + 外部模型服务
2. 云主机自建 Node + DB + Nginx

### 决策

采用托管部署方案。

### 理由

- 上线快
- 运维复杂度低
- 便于 preview / staging / production 环境管理

### 代价与权衡

- 平台耦合更高
- 定制能力弱于自建

### 后续动作

- 环境变量按环境隔离
- 关键外部依赖故障要有降级策略

## ADR-010：MVP 不提前引入 Redis、消息队列和独立分析链路

### 状态

Accepted

### 日期

2026-03-23

### 背景

当前系统虽然包含 AI 调用、会话存储、积分更新和埋点分析，但负载规模仍处于可由单体 + 事务库承载的阶段。

### 备选方案

1. 首版不引入 Redis / MQ / 独立数仓
2. 从一开始引入缓存、队列和分析仓库

### 决策

MVP 阶段不提前引入这些组件，仅在代码和接口层为后续演进保留边界。

### 理由

- 降低系统复杂度
- 减少部署和观测面
- 让团队专注于产品闭环验证

### 代价与权衡

- 某些高频场景性能优化空间有限
- 后续增长期可能需要补基础设施

### 后续动作

- 监控 AI 接口耗时和关键查询耗时
- 当消息量或事件量达到阈值时，再引入缓存或异步队列

---

## 结论

这些 ADR 的共同目标，不是追求“最先进”的架构，而是确保当前阶段的技术路线服务于产品验证：以最低复杂度支撑学习闭环，以清晰边界保证后续演进，以可观测性支撑业务判断。只要这些关键决策稳定，团队就能在 MVP 阶段保持速度和技术秩序。

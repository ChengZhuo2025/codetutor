## 1. 文档摘要

AI编程学习教练是一款面向中文用户的 AI 编程学习陪练产品，核心价值不在于“提供更多教程”，而在于把零散教程、视频、代码片段和学习资料转化为可执行、可追踪、可反馈的学习过程。产品通过 AI 导师对话、分步闯关、学习进度追踪和基础激励机制，帮助用户从“看过”走向“做成”。

MVP 阶段聚焦三个核心问题：

1. 用户不知道从哪里开始学 AI 编程工具。
2. 用户能找到教程，但无法拆解成可执行步骤。
3. 用户在实践过程中容易卡住、中断、放弃，缺少持续陪练和正反馈。

本 PRD 目标是明确 MVP 的产品范围、关键需求、优先级、成功指标和验收标准，为设计、研发和测试提供统一执行依据。

### 1.1 当前前端原型校准说明

当前仓库内已存在可运行的前端原型，实际覆盖以下页面：

1. `/` 营销首页
2. `/login` 登录页
3. `/onboarding` 三步式新手引导
4. `/learn` 学习工作台
5. `/map` 当前学习计划地图
6. `/achievements` 成长反馈页
7. `/history` 历史学习计划页

本次 PRD 校准遵循以下原则：

- 以当前前端原型已经稳定表达的真实功能需求为准，不再以更早的概念方案文档为准。
- `/history` 当前承载的是“历史学习计划列表”，不是“最近会话消息列表”。
- `/map` 当前承载的是“当前激活学习计划的线性闯关地图”，不是多计划分发入口。
- FAQ、订阅展示块、营销文案、图标和颜色 token 仍属于前端展示层，不作为 MVP 首期后端权威需求。

### 1.2 当前代码实现快照

截至当前仓库代码，MVP 中已经真实打通的用户主链路包括：

- 手机验证码登录、登录后自动判断进入 `/onboarding`、`/learn` 或 `/history`
- 已登录用户回到首页时可自动恢复登录态，首页 CTA 会切换为“继续学习”，并按真实学习计划状态推荐去向
- onboarding 完成后创建真实 `user_learning_path` 与 `user_tasks`
- `/learn`、`/map`、`/achievements`、`/history` 读取真实接口与远程数据库
- 用户个人资料编辑、头像上传、头像存储
- 用户建议反馈提交、我的反馈记录、管理员回复接口
- 历史学习计划管理：放弃进行中计划、重新激活中断计划、查看计划复盘、删除历史记录

当前仍保留为静态或占位的能力包括：

- 订阅模块
- FAQ 内容
- 通知设置落库
- 管理员后台前端页面
- 打卡写接口、埋点写接口与任务完成写接口

因此，本文档中的产品范围以“用户可见功能口径”为主；如涉及实现状态，以本节快照和代码为准。

## 2. 产品背景与机会

### 2.1 背景

AI 编程工具快速普及，用户对 Cursor、Claude Code、Codex CLI、Trae、Kiro 等工具的学习需求持续增长。但当前市场上的主流供给以教程、课程、直播、视频内容为主，普遍存在以下问题：

- 学习内容分散，用户需要自己筛选与组织。
- 教程偏“展示结果”，缺乏过程引导和卡点处理。
- 用户收藏很多内容，但真正完成实践的人比例较低。
- 初学者对工具、Prompt、调试、项目拆解缺乏系统认知。

### 2.2 市场机会

面向中文市场，存在“AI 编程内容消费”向“AI 编程能力训练”迁移的机会。用户并不缺教程，缺的是把教程转换成行动路径、在卡住时得到及时支持，并持续获得学习反馈的产品。

### 2.3 产品定位

一句话定位：

> 你负责找到想学的内容，我负责陪你真正学会。

定位说明：

- 不是教程分发平台，而是学习执行层产品。
- 不是通用聊天助手，而是围绕 AI 编程学习场景优化的教练型助手。
- 不是重社区型产品，MVP 以个人学习闭环为核心。

## 3. 产品目标

### 3.1 业务目标

在 MVP 阶段验证以下核心假设：

1. 用户愿意将教程、链接、代码片段交给 AI 进行学习拆解。
2. “只给下一步”的学习方式能显著提升执行率与完成率。
3. 学习陪练 + 进度追踪 + 轻量激励机制能够提升留存。

### 3.2 用户目标

- 入门用户可以完成第一个 AI 编程实践任务。
- 有基础用户可以建立可复用的 AI 编程工作流。
- 用户能清楚知道“下一步做什么”和“自己已经学到了什么”。

### 3.3 成功指标

MVP 建议追踪以下指标：

| 指标 | 定义 | 目标建议 |
|------|------|---------|
| 激活率 | 新注册用户 24 小时内完成首次引导三步并发起首次 AI 对话 | >= 60% |
| 首日任务完成率 | 完成至少 1 个学习步骤的用户占比 | >= 45% |
| 7 日留存 | 注册后第 7 天仍有学习行为的用户占比 | >= 25% |
| 首次成就达成率 | 在 7 天内获得首个段位或累计达到指定学分的用户占比 | >= 35% |
| 学习连续性 | 人均每周有效学习天数 | >= 2.5 天 |
| AI 对话有效率 | 用户主动标记“有帮助”或完成下一步任务的对话占比 | >= 70% |

说明：目标值为 MVP 建议值，正式上线前可结合内测数据调整。

## 4. 目标用户与细分人群

### 4.1 核心用户

| 用户层级 | 典型画像 | 核心诉求 | 主要障碍 |
|------|------|------|------|
| 入门用户 | 产品经理、设计师、创业者、运营 | 希望低门槛做出第一个应用 | 不会选工具，不会写 Prompt，不会排错 |
| 进阶用户 | 有前端/后端基础的开发者 | 希望提升 AI 编程效率，形成工作流 | 学得零散，缺少系统方法 |
| 高阶用户 | 有一定项目经验，希望系统化提升的人 | 希望跨工具选型、优化流程、补齐方法论 | 已有认知碎片，但缺乏结构化训练 |

### 4.2 MVP 首要服务对象

MVP 优先服务两类用户：

1. 有明确学习意愿，但尚未形成 AI 编程方法的入门用户。
2. 已经在使用 1 至 2 个 AI 编程工具，但希望提升效率的进阶用户。

原因：

- 需求更明确，付费意愿更容易被验证。
- 更容易通过“第一成果”和“效率提升”感知价值。
- 训练路径与产品功能更适合 MVP 快速落地。

## 5. 用户问题定义

当前用户在学习 AI 编程工具时主要面临以下问题：

1. 不知道该学哪个工具，选型成本高。
2. 看过教程，但不会将内容转化为自己的实践任务。
3. 学习过程中常常卡在很小的问题上，导致中断。
4. 不知道自己的学习进度和阶段，不容易积累成就感。
5. 缺少持续反馈机制，学习容易半途而废。

---

## 6. 核心价值主张

产品提供以下核心价值：

- 帮用户把教程转成“今天就能做”的步骤。
- 在学习过程里以教练方式提问、提示、纠偏，而不是直接替用户完成。
- 持续记录学习路径、知识点和进度，降低中断成本。
- 通过学分、段位、连续打卡等轻量机制增强成就感和持续性。

## 7. 产品范围

### 7.1 MVP 范围

MVP 必须包含以下能力：

| 模块 | 是否纳入 MVP | 说明 |
|------|------|------|
| 用户账号系统 | 是 | 登录、注册、基础用户信息、学习记录绑定 |
| 个人资料管理 | 是 | 用户可修改昵称、微信号、邮箱、简介，并上传头像 |
| 工具选择 | 是 | 用户首次进入时选择目标 AI 编程工具 |
| AI 导师对话 | 是 | 核心功能，支持文本类学习输入与对话陪练 |
| 学习步骤拆解 | 是 | AI 将教程或问题拆解为当前可执行下一步 |
| 学习进度追踪 | 是 | 记录学习路径实例、当前任务、地图进度、历史学习计划 |
| 基础学分系统 | 是 | 支持完成步骤、打卡获得学分 |
| 段位系统 | 是 | 基于学分展示成长反馈 |
| 闯关式任务视图 | 是 | 用于承载“下一步”推进逻辑，可先做简版 |
| 用户建议反馈 | 是 | 用户可提交建议/问题反馈，查看自己的反馈记录和官方回复 |
| 教程链接解析 | 是 | 支持用户提交外部教程链接并生成学习引导 |
| 截图上传解析 | 否，延后 | 前端原型可保留截图文案入口，但首期后端不作为必做能力 |
| 排行榜/社区 | 否 | 不进入 MVP |
| 邀请裂变 | 否 | 不进入 MVP |
| 移动端 App | 否 | 首版以 Web 为主 |
| 支付系统 | 否 | 商业模式先定义，支付接入延后 |

补充说明：

- 当前前端原型中的订阅卡、FAQ、营销模块继续保留，但它们属于展示层或未来商业化预留，不构成首期后端建设范围。
- MVP 首期真正需要打通的是 `login -> onboarding -> learn -> map -> achievements -> history` 这条个人学习闭环。

### 7.2 非目标

以下内容明确不属于本期目标：

- 搭建教程内容平台或课程商城。
- 构建开放式开发者社区。
- 提供企业级团队协作与管理员后台。
- 在首版中支持所有 AI 编程工具的深度定制教学。
- 通过 AI 直接替用户生成完整项目并弱化学习过程。

## 8. 用户场景与 JTBD

### 8.1 典型场景

场景 A：用户在 B 站、YouTube、公众号或社媒上看到一个 AI 编程教程，觉得很有用，但看完后不知道怎么开始实践。  
产品机会：把内容拆解成结构化学习步骤，并带着用户执行第一步。

场景 B：用户已经在使用 Cursor 或 Claude Code，但经常停留在“会一点但不系统”的阶段。  
产品机会：围绕指定工具提供分层路径与阶段目标。

场景 C：用户写 Prompt、生成页面或调试代码时卡住，不知道该继续尝试还是换方向。  
产品机会：AI 教练根据当前上下文提供提示、追问和纠偏建议。

### 8.2 JTBD

当我想学会一个 AI 编程工具并做出实际成果时，我希望有一个能理解我当前水平、把教程拆成可执行任务、并在我卡住时持续陪练的助手，这样我就能真正学会，而不是只停留在收藏和浅尝阶段。

## 9. 核心用户流程

### 9.1 首次使用流程

1. 用户进入 Landing Page，理解产品价值。
2. 用户登录/注册。
3. 用户选择目标工具或学习方向。
4. 系统展示对应的初始学习路径或建议起点。
5. 用户选择“平台预设训练”时，可直接进入第一关；选择“自学模式”时，再提交教程文本、代码片段或链接开始练习。
6. AI 导师解析内容或载入预设任务，生成当前第一步学习任务。
7. 用户完成步骤后获得学分，并进入下一步。

### 9.2 日常学习流程

1. 用户回到产品首页。
2. 若用户仍处于有效登录态，系统会在首页直接恢复会话摘要并展示“继续学习”入口。
3. 若存在 `active` 计划，则进入 `/learn`；若无 `active` 但已有历史计划，则进入 `/history`；若没有任何学习计划，则进入 `/onboarding`。
4. 用户继续当前任务，或提交新的教程/问题。
5. AI 导师根据历史上下文给出下一步引导。
6. 用户完成任务并更新学分、段位、连续打卡等状态。

### 9.3 卡住求助流程

1. 用户在当前任务节点点击“我卡住了”或直接输入问题。
2. AI 识别当前阶段与上下文。
3. 系统优先给提示、分解和排查方向，而不是直接给最终答案。
4. 若用户连续多次无法推进，可降级任务难度或回退到前置知识点。

## 10. 功能需求

### 10.1 模块一：账号与身份系统

### 目标

建立用户身份与学习数据的绑定关系，支持后续进度存储、个性化推荐和商业化转化。

### 需求说明

- 支持手机号登录。
- 支持微信登录。
- 首次登录后创建用户档案。
- 档案至少包含：昵称、登录方式、选择的主学习工具、当前阶段、学分、段位、连续打卡天数。

### MVP 验收标准

- 用户可在 1 分钟内完成登录并进入学习主流程。
- 登录成功后可正确读取或创建个人学习档案。
- 同一用户再次登录后可恢复历史学习记录。

### 10.2 模块二：初始学习定向

### 目标

帮助用户在首次进入时完成主工具、当前水平与起始训练路线的定向，避免一上来信息过载。

### 需求说明

- 首次进入时必须完成三步引导：选择主学习工具、确认当前水平、选择起始学习路线。
- 工具列表按“图形化工具 / CLI 工具 / 轻量在线工具”分类展示。
- 用户首次引导阶段只选择 1 个主学习工具。
- 系统根据所选工具与用户水平，展示不同的起始学习路线选项。
- 起始学习路线至少包含两类来源：
  - 自学模式：用户自行粘贴教程、代码或链接开始练习
  - 平台预设训练：由后台配置的训练 agent 与训练路径
- 平台不做教程内容分发，但提供可配置、可分阶段扩展的训练任务体系。
- 支持后续切换或新增工具方向。

当前原型补充约束：

- 自学模式卡片可以保留“截图”文案作为未来扩展提示，但不要求 MVP 首期后端已具备图片解析能力。
- 平台预设训练卡片当前前端已稳定表达 `stageCount`、`coachAgentLabel`、`estimatedDuration`、`tags`、`preview` 等信息，后续服务端应按这些真实业务字段供给。

### MVP 验收标准

- 用户完成三步引导后，系统能写入主工具、学习水平与起始路线选择结果。
- 不同工具和不同水平至少有不同的平台预设训练路线。
- 即使没有命中的平台预设训练路线，用户仍可通过自学模式进入学习主流程。
- 用户返回时能看到当前工具与当前路线对应的学习上下文。

### 10.3 模块三：AI 导师对话

### 目标

作为产品的核心引擎，负责理解用户输入内容并将其转为可执行、可追踪的学习动作。

### 输入范围

MVP 支持：

- 粘贴教程文字
- 粘贴代码片段
- 提交网页或视频链接
- 自然语言提问

后续版本支持：

- 截图上传解析
- 更丰富的多模态输入

说明：

- 当前前端原型中已存在图片附件和截图相关展示位，但它们在 MVP 首期仍视为前端预留能力，不要求首期后端和数据库强制支持。

### 核心行为规则

AI 导师需要遵循以下原则：

1. 先识别用户水平和学习意图。
2. 先拆解任务，再推进执行。
3. 优先使用提问、提示和引导，不直接给完整答案。
4. 永远给出“当前这一步要做什么”。
5. 用户完成后要总结收获并指向下一步。

### 对话输出要求

每轮核心输出至少包含以下内容中的 2 至 3 项：

- 当前目标
- 当前只需完成的一步
- 如果卡住可尝试的提示
- 完成后你将学会什么
- 下一步预告

### MVP 验收标准

- 用户提交有效输入后，系统在可接受时间内返回学习引导。
- 引导内容应包含明确行动项，不仅是概念解释。
- 用户在至少 70% 的对话中能继续产生下一步行为。
- 系统能够保存对话历史并关联到具体学习任务。

### 10.4 模块四：闯关式学习任务

### 目标

将抽象学习过程转化为清晰、低压力、可推进的任务链路。

### 需求说明

- 每个学习路径由若干任务关卡组成。
- 每次主界面默认只突出展示当前任务与下一步。
- 任务应有状态：未开始、进行中、已完成、卡住。
- 已完成任务应有明显反馈。
- 当前任务支持用户主动标记完成或重新求助。

### MVP 实现要求

- 可先采用线性关卡结构，不强制首版实现复杂分支。
- 至少支持展示前置任务、当前任务、下一任务。
- 每个任务需与一个或多个知识点标签绑定。

### MVP 验收标准

- 用户可以明确知道自己当前位于哪一关。
- 完成任务后系统能自动解锁下一步或推荐下一步。
- 历史已完成任务可回看。

### 10.5 模块五：学习进度追踪

### 目标

让用户清楚感知自己学过什么、卡在哪里、接下来做什么。

### 需求说明

- 记录学习路径、任务完成情况、最近一次对话时间、累计学分、段位。
- 主界面展示当前阶段、当前任务和进度概览。
- 用户再次进入时自动回到最近学习上下文。
- 至少支持查看历史学习计划、已完成任务和最近学习时间。

当前原型补充约束：

- `/history` 页当前展示的是“学习计划实例列表”，每条记录包含工具、模式、完成进度、XP 收益和更新时间。
- 当前产品主线应围绕“学习路径实例”组织，而不是围绕零散对话会话组织。
- 当前学习计划状态应至少区分 `active`、`interrupted`、`completed`、`abandoned`、`archived`。
- `interrupted` 为系统自动中断状态，当前阈值为连续 7 天无学习行为；`abandoned` 为用户主动放弃，不允许再次激活。

### MVP 验收标准

- 用户离开后再次进入可恢复最近学习状态。
- 主界面可在 5 秒内让用户理解“现在到哪了”和“接下来做什么”。
- 历史数据与当前任务状态保持一致。

### 10.6 模块六：学分与段位系统

### 目标

通过轻量激励增强学习反馈和连续性，但不喧宾夺主。

### 规则说明

建议沿用设计稿中的基础规则：

| 行为 | 学分 |
|------|------|
| 完成实战任务步骤 | +10 |
| 每日打卡 | +20 |
| 完成完整项目 | +100 |
| 分享学习成果 | +30 |
| 提交优质教程 | +25 |
| 帮助其他用户 | +15 |

MVP 阶段实际启用的加分项：

- 完成实战任务步骤
- 每日打卡
- 完成完整项目

延后启用的加分项：

- 分享学习成果
- 提交优质教程
- 帮助其他用户

### 段位规则

| 段位 | 学分范围 |
|------|------|
| 萌新码农 | 0 - 200 |
| AI学徒 | 200 - 500 |
| Vibe Coder | 500 - 1000 |
| AI建造者 | 1000 - 2000 |
| AI编程大师 | 2000+ |

### MVP 验收标准

- 学分在任务完成后实时更新。
- 用户可在个人页或主界面看到当前段位。
- 连续打卡和累计学分逻辑正确，不出现重复计分。

### 10.7 模块七：Landing Page 与转化入口

### 目标

让首次访问用户快速理解产品价值，并完成注册转化。

### 页面核心内容

- 一句话价值主张
- 三步工作方式说明
- 目标用户与适用工具展示
- 产品收益展示
- 免费开始 CTA

### MVP 验收标准

- 用户在首屏可理解产品是“学习陪练”而非“教程库”。
- Landing Page 到注册页的转化路径清晰。
- 已登录用户再次进入首页时，可直接看到当前账号状态与“继续学习”入口，而不是被误导回登录流程。
- 页面文案与产品内体验一致，不夸大承诺。

## 13. 数据埋点与分析需求

MVP 需要埋点以下关键事件：

| 事件名 | 触发条件 |
|------|------|
| `landing_cta_clicked` | 点击首页开始按钮 |
| `signup_completed` | 完成注册或登录 |
| `tool_selected` | 选择学习工具 |
| `first_session_started` | 发起首次 AI 导师对话 |
| `task_generated` | 系统成功生成学习任务 |
| `task_completed` | 用户完成一个任务步骤 |
| `stuck_help_requested` | 用户主动求助或点击“卡住了” |
| `daily_checkin_completed` | 完成打卡 |
| `rank_up` | 段位提升 |
| `session_resumed` | 回到上次学习上下文 |

分析维度建议：

- 按用户层级查看激活与留存。
- 按工具类型查看学习完成率。
- 按任务阶段查看卡点分布。
- 按输入类型查看 AI 对话有效率。

## 14. 非功能需求

### 14.1 性能

- 主界面首屏应快速可用，避免学习链路中断。
- AI 回复需在用户可接受范围内返回，并有明确加载反馈。

### 14.2 可用性

- 核心路径应适配桌面端主流浏览器。
- 文案应优先使用简洁中文，避免过强技术门槛。

### 14.3 数据与隐私

- 用户历史对话、学习记录需与账号绑定并安全存储。
- 用户提交的外部教程链接与代码片段需有明确的数据使用说明。

### 14.4 可扩展性

- 工具体系、任务模板、积分规则需要支持后续扩展。
- 订阅权限和支付能力需在架构上预留。

## 17. 上线验收标准

满足以下条件才可进入 MVP 内测：

1. 用户可完成注册、选择工具、发起首次学习、完成至少一个任务步骤的完整闭环。
2. AI 导师输出能够稳定生成明确的“下一步”动作，而不仅是泛化回答。
3. 学习记录、任务状态、学分与段位可正确保存和恢复。
4. 关键埋点可正常上报。
5. 研发、产品、测试三方对 P0 页面和流程完成走查。

## 18. 风险与待确认问题

### 18.1 主要风险

1. 如果 AI 导师过于像通用聊天机器人，用户难以感知差异化价值。
2. 如果任务拆解质量不稳定，用户可能无法持续推进。
3. 如果学分机制过重，会削弱产品的专业可信度。
4. 如果支持工具过多，首版路径和内容维护成本会迅速上升。
5. 如果没有支付接入，付费转化验证周期会拉长。

### 18.2 待确认问题

1. MVP 首批主推工具是否只保留 3 至 4 个，以提高教学质量与路径打磨效率。
2. 外部链接解析能力覆盖范围如何定义，是否区分网页、视频、图文。
3. AI 输出是否需要产品内固定模版，以确保“下一步”表达稳定一致。
4. 首版是否需要“我卡住了”快捷入口，还是通过自然对话统一承载。
5. 学分与段位是否需要在首版控制视觉权重，避免游戏化喧宾夺主。

## 21. 结论

AI编程学习教练的核心不是“再做一个 AI 内容产品”，而是构建一套围绕 AI 编程学习过程的执行系统。MVP 必须首先证明三件事：

1. 用户愿意把学习输入交给 AI 教练处理。
2. AI 拆解后的“下一步”确实能推动用户行动。
3. 学习进度与轻量激励能提升持续学习意愿。

如果上述三点成立，产品即可在第二阶段扩展到付费、社区、分享和更完整的工具生态。
